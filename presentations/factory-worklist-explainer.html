MO (ถ้ามี)
เกิดขึ้นก็ต่อเมื่อมีคนตัดสินใจแล้วเท่านั้น
Odoo standard Manufacturing app แสดงเฉพาะ MO ที่ ถูกสร้างแล้ว — ไม่มีหน้าจอไหนที่รวม SO Line จากหลายออเดอร์มาบอกว่า "เหล่านี้คืองานที่รอการตัดสินใจ" ได้เลย
งาน 3 แบบที่ Worklist ต้องรวมให้ดูในที่เดียว

ปลายทางไม่เหมือนกันเลยสักแบบ

ปุ่มบน Worklistใช้เมื่อไหร่ปลายทาง
Cut to Orderต้องตัดแผ่นใหม่จากก้อน (Mode 3)สร้าง Manufacturing Order (มาตรฐาน)
Produce FGต้องผลิตสินค้าสำเร็จรูปจากแผ่นที่มีอยู่ (Mode 5)สร้าง Manufacturing Order (มาตรฐาน)
Sell Whole Blockขายทั้งก้อนดิบ ไม่ตัดเลย (Mode 1)ไม่มี MO — จบที่ Sale Order Line เท่านั้น
3 ปุ่ม 3 ปลายทางต่างกันโดยสิ้นเชิง — นี่คือเหตุผลว่าทำไมจะดูจาก Manufacturing app อย่างเดียวไม่พอ เพราะ 1 ใน 3 กรณีไม่เกี่ยวกับ Manufacturing เลยด้วยซ้ำ

Worklist กรองงานให้ดู — ตัว Engine ที่ทำงานจริงเป็น Standard ทั้งหมด

สร้าง mrp.production จริง + action_confirm()
เดินตาม state machine มาตรฐาน (Confirmed → In Progress → Done)

Wizard เปิดให้เลือกก้อนที่จะขาย
กด Confirm

ไม่มี Production ใดๆ เกิดขึ้น — ขายก้อนดิบตรงๆ
จุดสำคัญ: Worklist เองไม่ได้ "ทำงาน" อะไรเลย มันแค่กรอง Sale Order Line ที่ยังไม่ถูกจัดการมาแสดงรวมกัน แล้วส่งต่อให้ Wizard ที่มีอยู่แล้วทำงานต่อ — ตัวที่สร้าง/ควบคุม MO จริงคือโค้ดมาตรฐานของ Odoo (mrp.production) ทั้งหมด
ทำไมไม่ใช้หน้า Manufacturing Orders ของ Odoo แทนไปเลย

เพราะ ณ จุดที่ต้องใช้ Worklist — MO ยังไม่เกิดขึ้นด้วยซ้ำ

ถ้าใช้แค่ Manufacturing app มาตรฐาน
มองไม่เห็นงานที่ยังไม่ตัดสินใจ
หน้า MO list แสดงเฉพาะ MO ที่ถูกสร้างแล้ว — SO Line ที่ยังรอให้คนตัดสินใจว่าจะ Cut/Produce/Sell Block จะไม่ปรากฏที่ไหนเลย ต้องเปิด Sale Order ทีละใบไล่เช็คเอง
ด้วย Factory Worklist
เห็นงานค้างข้ามทุก SO ในหน้าเดียว
กรองอัตโนมัติจาก field เดียว (stone_factory_action_needed) รวมงานทุกประเภทจากทุก Order มาไว้ที่เดียว พร้อมปุ่มลัดเข้า Wizard ที่ถูกต้องของแต่ละแบบ
Worklist ไม่ได้แข่งกับ Manufacturing app — มันทำงานก่อนหน้า MO app จะมีอะไรให้ดูด้วยซ้ำ ทั้งสองอยู่คนละจุดในไทม์ไลน์เดียวกัน
สรุปภาพรวม

Standard Odoo เต็มรูปแบบ + Custom เฉพาะจุดที่จำเป็นสำหรับ EG

SO Confirmed→ Worklist (custom กรอง+รวมงาน)→ MO / Production (standard 100%)
ส่วนที่เป็น Standard เต็มที่
Manufacturing Order, BOM, state machine, stock move, การนับสต็อก — ทั้งหมดเป็นกลไก Odoo ล้วนๆ ไม่มีการแก้ core หรือ fork ระบบผลิตของ Odoo แม้แต่จุดเดียว
ส่วนที่ Custom เพื่อ EG โดยเฉพาะ
แค่ "หน้าจอรวมงานก่อนเริ่มผลิต" ที่ Odoo ไม่มีให้ตั้งแต่ต้น — เพราะธุรกิจนี้มี 3 เส้นทางงานที่ปลายทางต่างกัน (2 เข้า MRP, 1 ไม่เข้า) ซึ่งไม่ตรงกับสมมติฐานของ Manufacturing app มาตรฐาน
รายละเอียดโค้ดจริงที่ยืนยันเรื่องนี้ อยู่ในภาคผนวกถัดจากนี้

สำหรับทีม
อ้างอิงตรงจากไฟล์จริงในโมดูล stone_slab_inventory (EE branch) — ไม่จำเป็นต้องนำเสนอให้ลูกค้าดูในรอบปกติ
อ้างอิงไฟล์จริง

แต่ละปุ่มเรียกอะไร — เห็นได้จาก 3 ไฟล์นี้

ปุ่มไฟล์สิ่งที่เกิดขึ้นจริงในโค้ด
Cut to Order stone_cut_order_wizard.py MrpProduction.create({...}) ตามด้วย production.action_confirm() — เรียก API มาตรฐานของ MRP ตรงๆ ไม่มีการ override behavior
Produce FG stone_fg_production_wizard.py เหมือนกันทุกจุด: สร้าง mrp.production จริง + action_confirm() รวมถึงสร้าง byproduct move ตามรูปแบบมาตรฐานของ MRP core
Sell Whole Block stone_block_select_wizard.py เขียนแค่ stone_bundle_id / product_uom_qty ลง sale.order.line — ไม่แตะ mrp.production เลยแม้แต่บรรทัดเดียว
Worklist เอง stone_factory_worklist_views.xml เป็น list view บน sale.order.line กรองด้วย domain [('stone_factory_action_needed', '=', True)] — ไม่มี business logic ของตัวเอง มีแค่ปุ่มเรียก 3 wizard ข้างต้น
สรุปภาคผนวก: ทุกจุดที่แตะ Manufacturing เป็นการเรียก Odoo API มาตรฐานตรงๆ (create() + action_confirm()) — Worklist ไม่มี logic ผลิตของตัวเองแม้แต่บรรทัดเดียว มีหน้าที่เดียวคือ "รวมงานที่ต้องตัดสินใจ" แล้วส่งต่อให้กลไกมาตรฐานทำงานต่อ
