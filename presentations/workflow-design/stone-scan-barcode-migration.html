6. เขียน status กลับ (skip_stock_move=True)
slab.with_context(skip_stock_move=True).write({'status': target})
ทำไมต้องมี context flag: ถ้าเขียน status ตรงๆ โดยไม่กัน จะเข้า write() override เดิมที่พยายามสร้าง stock.move ซ้ำอีกรอบ (ทั้งที่ move จริงเกิดจาก picking ไปแล้วในขั้นตอนที่ 3) — context นี้มีอยู่แล้วในโค้ดปัจจุบัน (stone_slab.py:287) แค่ยังไม่เคยถูกเรียกจากทิศทางนี้
ไม่ถูกแตะเลย: Check Stock (โหมด cycle count ของ /stone-scan) ใช้โมเดล stone.stock.take แยกต่างหาก เทียบ "สแกนเจอจริง" กับสถานะที่คาดไว้ แล้ว export Excel — อ่าน stone.slab.status เหมือนเดิม ไม่ขัดกับ flow ใหม่ด้านบนเลย เพราะ status field ยังถูก sync ให้ถูกต้องอยู่ (ผ่าน hook ข้อ 4-6) แนะนำเก็บไว้ตามเดิมในเฟสแรก
สรุปสั้นๆ
ฝั่งซ้าย (วันนี้) มี custom code 4 จาก 5 ขั้นตอน แต่ทั้งหมดกระจุกอยู่ใน controller เดียว ง่ายต่อการเข้าใจ — ฝั่งขวา (เสนอ) ลดจำนวนจุด custom เหลือ 3 จุด แต่ทั้ง 3 จุดนี้เป็น โค้ดใหม่ที่ต้องเขียนเพิ่ม (ไม่ใช่แค่ย้ายของเดิม) เพื่อปิดช่องว่างที่ Barcode app มาตรฐานไม่รู้จัก business rule ของหินเลย — นี่คือเหตุผลที่บอกไปก่อนหน้าว่า "โค้ดที่ลดได้กับที่ต้องเพิ่มใหม่ใกล้เคียงกัน" ไม่ใช่การลบทิ้งได้ฟรีๆ
